# SESSION_COPILOT — Growing Math
Data de início : 2026-08-31 08:22
Projeto        : Growing Math (C:\Growing Math)
Objetivo       : Plataforma de aprendizagem adaptativa de matemática, gamificada (RPG),
                 com IA (Gemini / Ollama), empacotada como app desktop Electron para Windows.
Stack          : React 19 + Vite 6 + TypeScript + TailwindCSS 4 + react-router-dom 7
                 Express 4 + better-sqlite3 (SQLite local) + @google/genai + Ollama
                 Electron 36 + electron-builder (NSIS) + esbuild (bundle do server)

## Arquitetura (resumo)
- server.ts (~140 KB, monolito): Express + SQLite + IA + auth JWT-like próprio + serve o front
  (Vite middleware em dev, dist/ em prod). Exporta startServer({port, host}).
- electron/main.mjs: sobe o backend em porta efêmera (127.0.0.1), carrega a URL na BrowserWindow,
  DB em app.getPath("userData")/growing_math.db, lê segredos de .env/growing-math.env.
- Dois bundles de front (multi-entry no vite.config.ts):
  - index.html   -> src/main.tsx        -> src/App.tsx           (app do ALUNO)
  - teacher.html -> src/teacher-main.tsx -> src/TeacherAccessApp.tsx (portal do PROFESSOR)
- src/services/geminiService.ts: camada client (chama /api/ai/*, cache de tutor em localStorage,
  gerador de exercícios offline/fallback determinístico).

## Domínio / features
- Aluno: trilhas (TOPICS em src/types.ts), combate RPG (CombatView) com exercícios de IA,
  XP/moedas/nível/streak, classes de herói (Guerreiro/Mago/Arqueiro), inventário e equipamento
  por slot (weapon_1h/weapon_2h/shield/armor/accessory), loja, conquistas, missões (quests),
  ranking, desafio diário determinístico por seed, tutor IA em chat, árvore de crescimento.
- Professor: turmas + código de turma, dashboard pedagógico, relatórios por turma,
  personalizações por aluno, recomendações, comunicados.
- Modo demo: usuário demo@growingmath.app e demo.prof@growingmath.app + AutoDemoDirector
  (tour automático de telas) — controlado por GROWING_MATH_DEMO.

## IA
AI_PROVIDER=auto|gemini|ollama. auto -> Gemini se houver GEMINI_API_KEY/GOOGLE_API_KEY,
senão Ollama local (OLLAMA_BASE_URL, OLLAMA_MODEL, default tinyllama:1.1b), senão fallback
offline determinístico (fallbackExercise / buildOfflineTutorResponse).

## Build / versionamento
- npm run dev            -> rebuild better-sqlite3 (node) + tsx server.ts
- npm run pack:installer -> scripts/versioning.mjs: bump de patch, arquiva release atual em
                            versionamento/v<versão>, e roda pack:installer:base
- pack:installer:base    -> electron-rebuild + build:main + build:teacher + build:server + NSIS
- Versão atual: 0.0.90 (histórico completo em versionamento/, v0.0.0 .. v0.0.89)

## Pontos de atenção
- server.ts e src/App.tsx são arquivos gigantes (140 KB / 184 KB) — candidatos a modularização.
- "name" do package.json ainda é "react-example".
- growing_math.db versionado na raiz (dev); em produção fica em userData.
- Segredos: AUTH_JWT_SECRET e TEACHER_ACCESS_CODE são OBRIGATÓRIOS quando HOST != loopback
  (o servidor recusa iniciar). Em modo desktop local são gerados e persistidos na tabela
  app_secrets. Ver env.example. Nunca commitar .env.
- Pasta não é repositório git.
- better-sqlite3 aplica FOREIGN KEYs por padrão (constraints do schema SÃO validadas).

Fluxo do install-ai.ps1:
1. Detecta o proxy do Windows e exporta HTTP_PROXY/HTTPS_PROXY (processo + escopo
   de usuario). CRITICO: o Ollama e escrito em Go e NAO le o proxy do Windows —
   sem isso o download do modelo trava em "pulling manifest" na rede Deere.
2. Baixa e instala o OllamaSetup.exe (~1,5 GB) em modo /VERYSILENT, por usuario,
   sem admin (compativel com allowElevation: false).
3. Reinicia o Ollama via "ollama app.exe" (tray), que registra o autostart.
4. Baixa o modelo pela API HTTP /api/pull (NDJSON com progresso).
5. Valida com uma geracao real ("12 + 7") e mede a latencia.
6. Grava $INSTDIR\.env com AI_PROVIDER, OLLAMA_MODEL e OLLAMA_BASE_URL.
Em qualquer falha: grava AI_PROVIDER=auto (modo offline) e sai com codigo 0 —
falta de IA nunca quebra a instalacao. Log em %LOCALAPPDATA%\GrowingMath\install-ai.log.
Atalho "Growing Math - Configurar IA local" no menu Iniciar permite tentar de novo.

Correcoes de runtime necessarias para a IA realmente funcionar:
- server.ts: o timeout de 12s valia tambem para /api/chat. Um modelo local em CPU
  quase nunca responde nesse tempo, entao TODA geracao abortava e caia no fallback
  em silencio. Agora sao dois timeouts: sondagem 5s e geracao 120s
  (configuravel por OLLAMA_TIMEOUT_MS).
- server.ts: OLLAMA_MODEL era usado sem validacao; nome errado quebrava tudo sem
  aviso. Agora e conferido contra /api/tags, com log e deteccao automatica.
- electron/main.mjs: ensureOllamaRunning() sobe o Ollama no boot do app se o
  usuario tiver fechado o tray.

Bugs encontrados e corrigidos durante os testes reais (nenhum apareceria sem executar):

BLINDAGEM CONTRA ConstrainedLanguage (install-ai.ps1)
Políticas WDAC/AppLocker variam por máquina. Nesta imagem
UsermodeCodeIntegrityPolicyEnforcementStatus=0, por isso o PS 5.1 está em
FullLanguage. Numa máquina com essa política ativa, Add-Type, New-Object
(HttpClient), [Console]::Out e [System.Net.WebRequest] lançam exceção e o
bootstrap morreria. Cada caminho ganhou equivalente só com cmdlets:
  - Write-Stage        → Write-Host (fora do pipeline, não polui retorno)
  - download do setup  → Invoke-WebRequest -OutFile (sem % de progresso)
  - pull do modelo     → POST /api/pull com stream=false (JSON único no fim)
  - persistir proxy    → Set-ItemProperty em HKCU:\Environment
  - detectar proxy     → registro WinINET + parser de PAC
Novo switch -ForceRestrictedMode permite testar o caminho degradado sem precisar
de uma máquina com WDAC restritivo.

PROXY POR PAC (descoberta importante)
A rede Deere NÃO usa proxy estático: ProxyEnable=0 e
AutoConfigURL=http://pac.deere.com/johndeere.com/deere.pac. O fallback por
registro retornava nulo, e em modo restrito o ollama pull travaria. Get-ProxyFromPac
baixa o PAC como texto, extrai os literais "PROXY host:porta" e TESTA cada um.
O alvo da sonda é https://registry.ollama.ai/v2/library/qwen2.5/manifests/0.5b
(HTTP 200) e não /v2/ — este responde 404 mesmo com o proxy funcionando, o que
tornaria qualquer página de erro de proxy um falso positivo.

### 2026-09-21 10:00 — Preparação para hospedar os dados na AWS

Pedido: "a ideia seria apenas as informações ficarem no servidor, o app vai
rodar sempre localmente, então seria basicamente para banco de dados".

DECISÃO DE ARQUITETURA
Hospedar o server.ts + banco na AWS, e não ligar o app direto num banco remoto.
Dois motivos concretos:
 1. better-sqlite3 é SÍNCRONO e há 128 chamadas diretas de db.prepare/exec/
    transaction no server.ts. Qualquer driver de banco remoto é assíncrono →
    seria preciso reescrever todos os handlers.
 2. Ligar cada app direto no banco exigiria distribuir a credencial do banco
    para toda máquina; qualquer usuário poderia ler/alterar os dados de todos.
O app continua rodando e servindo a interface localmente; só as chamadas /api
vão para a nuvem. Modo local segue sendo o padrão e o fallback.

IMPLEMENTADO
- NOVO src/config.ts: resolve a base da API em RUNTIME (não em build, para que
  trocar de servidor não exija recompilar o instalador). Lê
  window.__GROWING_MATH_CONFIG__.apiBaseUrl, com fallback para
  import.meta.env.VITE_API_BASE_URL (usado no `npm run dev`, onde quem serve é
  o Vite). Exporta apiUrl(), getApiBaseUrl(), isRemoteApi().
- 41 chamadas fetch('/api/...') passaram a fetch(apiUrl('/api/...')) em App.tsx
  (21), TeacherAccessApp.tsx (14), DailyChallenge.tsx (3), FeedbackForm.tsx (1)
  e geminiService.ts (2 — uma dentro de postJson, que recebe a url por
  parâmetro). Confirmado que não há EventSource/WebSocket/XHR/sendBeacon.
- server.ts: injectRuntimeConfig() injeta a config no HTML logo após <head>,
  com escape de < e > para não permitir quebrar a tag <script>. O bloco de
  estáticos foi reordenado — as rotas de HTML vêm ANTES de express.static
  (agora com index:false), senão o static serviria o HTML cru sem a injeção.
- server.ts: corsMiddleware(). Aceita qualquer origem loopback por padrão
  porque a porta do app muda a cada inicialização. É seguro porque a auth é
  por Bearer token em header, não cookie — um site malicioso não tem o token.
  Configurável por CORS_ALLOWED_ORIGINS e CORS_ALLOW_LOOPBACK.
- server.ts: rota /api inexistente agora devolve JSON 404 em vez de cair no
  catch-all que servia index.html com status 200. Sem isso, com a API na AWS,
  qualquer erro de rota viraria "Unexpected token '<'" no res.json() do
  cliente, escondendo a causa real.
- electron/main.mjs: API_BASE_URL entrou na lista de chaves de loadRuntimeSecrets.
- NOVO DEPLOY-AWS.md e seção nova no env.example.
- NOVO scripts/smoke-remote.mjs (17 asserções) + scripts npm: smoke:prepare,
  smoke:security, smoke:remote e smoke (roda tudo).

COMO ATIVAR, QUANDO O SERVIDOR EXISTIR
